# Публикация и первый запуск в HG SDLC

## Что импортировать
Архив имеет тот же верхний каталог `aidlc/`, что референс. В нём `flows/`, `skills/`, `subagents/`, а рядом документация и результаты проверки. Все версии — 3.0. Кодинг-агент — **Qwen**, потому что приложенные Qwen flow и subagent definition задают подтверждённый native формат.

```text
aidlc/
  flows/<flow-id>/3.0/{FLOW.yaml,metadata.yaml}
  skills/<skill-id>/3.0/{SKILL.md,metadata.yaml,templates/,references/,...}
  subagents/<subagent-id>/3.0/{metadata.yaml,<subagent-id>.md}
  docs/                       # описание для команды
  manual.html
  validation/                 # фактические проверки поставки
```

Расположите `flows/`, `skills/` и `subagents/` непосредственно в корне каталожного Git-репозитория HG SDLC. Каталог методики и целевая монорепа продукта — разные назначения. Flow работает с **одним checkout продукта**, даже когда сам каталог публикуется из другого Git.
`source_ref: main` и корневые `source_path: flows/...`, `skills/...`, `subagents/...` — параметры размещения каталога, не пути в рабочей монорепе; при иной ветке обновите `source_ref` перед публикацией.

Опубликуйте skills и native subagents, затем связанные flows штатными средствами установленного HG SDLC. В архиве нет придуманного import CLI, отдельного workflow runner, Python-runtime, `.pdlc` конфигуратора или Claude fallback. Все сущности оставлены draft до собственного smoke в HG.

## Однократная подготовка среды
Для HG нужны доступный Git checkout монорепы, Qwen ACP с native subagent support и материализация вложенных файлов skills. Для команд — Bash, Git и Node 22.16+ для вложенного проверочного инструмента. Язык продукта не ограничен Node: `build.sh`/`e2e.sh` вызывают фактический Java/Go/Python/JavaScript toolchain проекта; его версии определяются manifest и lockfiles.

Node нужен checker-у, а не как второй runtime процесса. Для учебного API используется `node:sqlite` со статусом experimental в применённой версии Node; библиотека и токены примера не являются production-рекомендацией. Нужны изолированные writable temp/database и разрешённая loopback-сеть. UI-фиче дополнительно нужен подготовленный браузерный toolchain. Не устанавливать инструменты сетевым bootstrap по догадке и не подставлять production credentials.

## Smoke перед delivery
Запустите `hg-pdlc-catalog-smoke@3.0` на отдельном учебном checkout. Узел должен действительно прочитать `templates/stage-index.md` и `templates/rework.ftl` и вызвать native acceptance-auditor. Проверьте, что `docs/hg-catalog-smoke.md` виден как project artifact, а `smoke-notes.md` — как run artifact. Отсутствие native вызова или вложенного файла — блокер, не «эквивалентный мысленный review».

На human-smoke сначала задайте замечание с сохранением изменений, затем отдельное замечание с откатом. Проверьте сохранение текста замечания в обоих prompt, штатное восстановление рабочей базы и повторное получение полных outputs. После этого Approve. Данная операция проверяет инфраструктуру конкретного HG, но не качество продукта.

## Выбор рабочего flow
`hg-pdlc-feature-e2e@3.0` — brownfield и greenfield, интервью/PRD обязательны, архитектурный gate по риску. `hg-pdlc-feature-e2e-governed@3.0` — те же форматы, архитектурный gate обязателен; подходит для первого контролируемого пилота. `hg-pdlc-baseline-recovery@3.0` — отдельное восстановление документации без реализации фичи.

После выбора проекта и flow ВП вводит обычное описание фичи; фиксированный JSON входа не требуется. `ai-context` формирует change_id и mode, закрепляет один Git-корень и существующие соглашения. Исходное намерение явно включено в instruction через FreeMarker, как требует референс.

## Не скрывать ошибки доступа
Нет Git-корня, нельзя прочитать код, не доступны обязательные tools или секреты тестовой среды — это инфраструктурный блокер, **не greenfield**. При недостающих полномочиях используется human exception. Секрет не записывается в форму, project documents или test log; подключение выполняется защищённым механизмом среды.

## Повторяемость и одновременные задачи
Один flow-run использует один изолированный checkout/worktree монорепы и один change_id. Два запуска не должны писать в одни и те же файлы общего checkout. ID фиксируется единожды, а artifact_ref с node_id разрешается по результатам конкретного writer. Для набора документов передаётся один индекс с точными путями; широкий glob не является списком входов.

Нельзя использовать evidence прошлого запуска, когда поменялись код, согласованные требования или инструменты проверки. После такого изменения соответствующий review/command этап выполняется заново. Push/merge/release/deploy и измерение эффекта за границами данного каталога.
