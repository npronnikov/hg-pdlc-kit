# Brownfield и greenfield: одна монорепа, один связанный маршрут

## Brownfield: база уже существует
Вход — доступные код, manifests, схемы данных, действующие продуктовые спецификации и tests. Сначала агент определяет модули фичи, точки входа, права, контракты и актуальность документации. Нельзя повторно спрашивать у ВП то, что надёжно находится в репозитории.

`ai-baseline` сохраняет релевантный baseline: capabilities/rules, C4 AS-IS, наблюдаемые системные обязательства, inventory тестов. У каждого утверждения есть источник. Устаревший документ не «исправляется незаметно»: противоречие фиксируется; реализация не считается доказательством бизнес-намерения. Уже подтверждённые правила не заменяются догадкой агента.

Интервью закрывает только недостающие решения: цель, пользователи, границы, исключения, совместимость, данные и критерии приёмки. ВП видит найденный контекст, варианты и последствия, а не пустой технический опросник. Требование, которое можно проверить, формализуется в BR/AC; неизвестное с существенными последствиями блокирует утверждение.

Архитектура описывает **изменение относительно AS-IS**, сохраняемые инварианты и ADR. SRS фиксирует интерфейсы, состояния, ошибки, совместимость, миграцию и NFR. Тестовая модель включает новый пользовательский путь и затронутую регрессию; для UI — браузер, backend и реальные core-сервисы/данные. Моки ядра не могут выдаваться за E2E.

После кода, тестов и фактических проверок flow обновляет текущее представление продукта и оставляет связанный пакет change/evidence. Документированный известный дефект не становится требованием. Изменённый код инвалидирует старое доказательство, даже если имя файла не поменялось.

## Greenfield: исходной системы ещё нет
Доступный Git-корень пуст либо содержит только инфраструктурный scaffold. Агент подтверждает это наблюдением. `ai-baseline` создаёт proposed foundation, словарь и границы; AS-IS явно N/A. Нельзя дорисовывать существующие сервисы, пользовательскую базу, SLA или API из похожего примера.

Интервью дополнительно уточняет предметные сущности, необходимые первые пользовательские операции, способ идентификации, границы системы и ограничения стека. Агент предлагает минимальный сквозной срез, но не расширяет feature scope до платформы по собственной инициативе. Новые цели принимаются ВП и попадают в PRD.

После PRD архитектура выбирает минимально достаточные компоненты и сравнивает альтернативы. SRS описывает контракты новой системы. Тестовая модель создаётся до кода: исходное состояние, способ появления сущности, публичные действия и проверяемый результат. Scaffold, тестовая среда и fixtures — явные задачи плана, а не неопределённый «предварительный шаг» вне flow.

Для Ticket API из сквозного примера greenfield-интервью должно решить, входит ли создание Ticket в фичу или допускается заранее согласованная тестовая подготовка. Если создание входит в минимальный срез, появляются BR/AC/SR и E2E создания→чтения→смены приоритета. Legacy migration неприменим; вместо него модель проверяет первый запуск на пустой БД. Нельзя silently skip обязательный кейс старой модели — модель меняется осознанно до кода.

Далее работают те же nodes/skills/subagents и rework rules. В результате остаётся первая проверенная документационная база продукта, код и выполненные E2E, но не релиз. Отдельный greenfield execution не заявляется: в комплекте его постановка/маршрут, а фактический HTTP-прогон выполнен для brownfield Ticket API.

## Когда запускать recovery отдельно
При большой монорепе с разрозненными specs сначала удобно один раз выполнить baseline-recovery. Он не восстанавливает цель продукта «с достоверностью из кода», а разделяет observed/inferred/confirmed, передаёт спорные утверждения владельцу и сохраняет пригодную базу. Следующий feature-flow повторно проверяет актуальность затронутых разделов, а не слепо доверяет вчерашнему baseline.

## Контроль участия человека
Штатный low-risk delivery: пакетное интервью + PRD approval. Governed или риск прав/PII/необратимой миграции/ломающего контракта добавляет архитектурное согласование. При содержательном противоречии возможен дополнительный вопрос; минимальное участие не означает автоматическое изобретение ответа. Итоговое техническое подтверждение выполняется evidence checker-ом и независимым review, без обязательного ручного «передайте документ дальше».
