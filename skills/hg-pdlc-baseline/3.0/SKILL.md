# Исходная документация продукта

## Входы
change-index / recovery-index, context, текущие спецификации и код. Метод из `hg-pdlc-method`.
## Brownfield
1. Сопоставить доменные понятия, пользовательские действия, роли, данные, компоненты и маршруты выполнения.
2. Создать/уточнить `docs/product/business/capabilities.md`, `rules.md`, `architecture/as-is.md`, `components.json`,
   `system/as-is-srs.md`, `quality/test-inventory.md`, `glossary.md`, `baseline.md` по templates.
3. Восстановленные системные требования назвать «наблюдаемые», с path/HEAD/locator; не объявлять авторизацию безопасной
   только потому, что в коде есть условие. Бизнес-цель и мотивация неизвестны без product-spec/human evidence.
4. Сохранить существующие подтверждённые документы. Новый слой даёт ссылки на legacy docs, не создаёт конкурирующую истину.
   Восстановленную ошибку отметить «known defect», не превратить в обязательное требование будущего продукта.
5. Индекс тестов описывает обнаруженное покрытие и фактические результаты отдельно; не запускалось = not_run.
## Greenfield
Создать те же минимальные разделы с `status: proposed`, пустым AS-IS (неприменимо) и реальными неизвестными.
Не рисовать существующий сервис/БД. Компоненты TO-BE появятся только после PRD в architecture-нoде.
Выбор технологии до интервью — предложение; сохранять бизнес- и эксплуатационные ограничения отдельно.
## Выходы и согласование
Документы — project, `baseline-index.md` и рабочие проверки — run. В основном flow ВП подтверждает релевантные
бизнес-положения через PRD. В отдельном recovery-flow — один human-baseline перед финальным baseline-record.md.
Реконструкция не меняет application-код, не прогоняет feature delivery и не заявляет E2E acceptance.

## Общие ограничения
Работать только внутри текущей HG SDLC-ноды и одной монорепы. Общие правила — в подключённом `hg-pdlc-method@3.0`.
Шаблоны читать относительно фактически материализованного `SKILL.md`, а не из выдуманного пути каталога.
Не доступны обязательный ресурс или сабагент — зафиксировать блокер; не изображать вызов или проверку.
Не менять согласованный upstream: сообщить finding и вернуть работу соответствующему владельцу артефакта.
Полезные результаты — `scope: project`; промежуточные материалы — `scope: run`. Пути брать из контракта ноды.
Записать все declared artifacts и step-summary; один текст «готово» не является результатом.
