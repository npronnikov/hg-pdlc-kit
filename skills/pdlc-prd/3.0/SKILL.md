# PRD и бизнес-требования


## Работа
Прочти актуальные ответы human-interview, анализ и существующие продуктовые ограничения. Сохрани содержательные решения в project decisions.md с ID вопроса/ответа и ссылкой на native human-gate. Полная форма ответа остаётся run. Не приписывай человеку «approved», пока gate не пройден.
Создай PRD.md: 1) проблема и evidence; 2) пользователи/JTBD; 3) INT и проверяемая HYP; 4) метрика, baseline либо неизвестное, целевое значение, окно и guardrail будущего измерения; 5) in/out scope; 6) BR и правила; 7) journey и исключения; 8) AC Given/When/Then; 9) ограничения/совместимость/данные/права; 10) предположения/зависимости/риски; 11) открытые решения; 12) definition of ready и политика делегирования.
BR описывает ценность/правило, AC — наблюдаемую приёмку. Не подменяй их Java-классами. На каждом INT/HYP/BR/AC поставь anchor и создай trace/intent.json. Минимум один осмысленный INT/HYP/BR/AC; покрытие определяется содержанием фичи, а не минимальным количеством.
Проверь полный жизненный цикл затронутого поведения: начало, успешное завершение, запрет/ошибка, повтор, отмена при применимости, старые данные и нецелевые пользователи. Для неприменимого явно объясни N/A.
Если ответы неполны и влияют на намерение, сохрани draft-артефакты и route on_questions обратно в ai-discover с точными недостающими решениями. Не запускай архитектуру с выдуманным бизнес-решением. Иначе on_success к машинной проверке и независимому PRD review.
## Выход
project: PRD.md, decisions.md, trace/intent.json. Исходные документы не становятся approved через поле, написанное агентом: утверждение фиксирует command-seal-prd после human-prd-approval.
