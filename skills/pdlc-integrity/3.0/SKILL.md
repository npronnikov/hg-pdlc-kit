# Детерминированные проверки


Каталожный skill описывает контракты проверок, но не запускает второй оркестратор. Точный stdlib verifier встроен в command-prepare FLOW и одновременно приложен как resources/verify.py для аудита. Command-prepare записывает его в project pdlc/tooling/verify.py, если файл отсутствует или байтово совпадает. Никакой глобальной установки hgpdlc-v2 и доступа к каталогам .hgsdlc не требуется.
Каждая следующая command-нода сначала проверяет SHA256 verifier, затем вызывает конечную проверку. check сверяет типы/revisions/coverage/anchors, собирает project граф/матрицу, пишет промежуточный report в run. seal фиксирует полезный project-реестр принятого набора документов, но решение делает native human/policy transition. run запускает реальные argv без shell, хранит actual exit, timeout, свежесть и JUnit. finalize отказывает nonzero при несвежем/неполном результате.
Обычный неуспешный тест возвращается как failed в отчёте при exit 0 обёртки, чтобы следующий AI-узел мог выполнить native rework. Это НЕ successful test: его настоящий exit_code и все errors сохранены, а finalize проверяет их детерминированно. Ошибка самого контракта/инструмента и final gate завершаются nonzero.
Runtime-пути для сырых файлов имеют logical имена из produced_artifacts; HG материализует их по контракту приложенных command-примеров. Не ищи attempt-N на диске и не создавай собственный run-root. CHECK можно выполнить в общем завершающемся acceptance harness с отдельным ID; число CHECK нельзя прибавлять к E2E.
Предел проверки: синтаксические/структурные условия и фактическое исполнение не доказывают бизнес-полноту. Для этого обязательны review и решения ВП. Контроль SHA не заменяет OS-изоляцию от намеренно враждебного агента с правом записи во всё workspace.
