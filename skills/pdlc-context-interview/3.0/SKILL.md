# Анализ монорепозитория и интервью


## Вход
Исходная фича, manifest.json, текущий код и доступные продуктовые документы. До интервью изучи контекст, не начинай со стандартного списка вопросов без анализа.
## Работа
1. Определи brownfield/greenfield по файлам, а не названию проекта. Для brownfield исследуй затронутые UI/API/данные/тесты, источники pdlc/product, openspec, _bmad-output, docs и ADR. Для greenfield проверь brief, ограничения платформы и scaffold; отсутствие реализации назови явно.
2. `sources.json`: для каждого источника path, sha256, observed_at, тип (code/spec/decision), авторитетность и ограничения. Зафиксируй конфликты code↔spec, не решай автоматически, что код прав. `analysis.md`: исходное состояние, affected modules, инварианты, зависимости, готовность E2E-стенда, неизвестное.
3. Создай intent.md с исходным запросом как данными. Не изменяй его ради текущей реализации; при новом решении ВП добавь явную историю изменения намерения.
4. `interview.md` (run): компактное интервью ВП с контекстом найденного. Для каждого вопроса — ID, почему блокирует, варианты и рекомендованный вариант с основанием, [Answer]. Отдели подтверждение очевидного от действительно неизвестного. Спроси цель/персоны, границы, бизнес-правила, исключения, успех и ограничения риска. Не спрашивай ВП название класса, формат SRS или выбор тестового фреймворка.
5. Неизвестное не выдумывай. При отсутствии исходной фичи первый вопрос запрашивает проблему/цель. Для большой brownfield-базы укажи целесообразность bootstrap, но восстанови релевантный минимум здесь, чтобы не требовать ручного переноса контекста.
## Выход
project: intent.md, analysis.md, sources.json. run: interview.md. Отдельный repository-scout возвращает найденные файлы и факты, не пишет бизнес-требования от имени ВП.
